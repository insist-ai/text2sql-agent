# NL2SQL 智能问数系统 · 简历写法与面试追问手册

> 用法：直接抄第二节的条目上简历；第三节是**每条被追问时的应答定位**，面试前过一遍。
> 所有数字都来自 `evaluation/report.md` 与 `evaluation/ablation.md`，面试时问到"这个数怎么来的"要答得出。

## 一、三条使用原则

1. **一条 bullet = 一个动作 + 一个量化结果 + 一个技术点**。没有数字的条目删掉或补数。
2. **写"我做了什么决策"，不只是"用了什么"**。"用 Redis 做缓存"是废话；
   "缓存键按『问题+数据范围』设计、带历史一律不命中以避免跨会话污染"才是你的东西。
3. **每一条都要能扛三层追问**：为什么这么做 → 备选方案为什么不选 → 代价是什么。
   第三节逐条备好了。

## 二、简历正文（可直接用）

### 项目名

**NL2SQL 智能问数系统 —— 基于大模型 Agent 的自然语言问数平台** | 个人项目 | 2026.03 - 2026.10

> 技术栈：Python · FastAPI · LangGraph · MySQL · Elasticsearch · Qdrant · Redis · Docker · Vue3

### 一句话描述（放项目名下面）

> 面向电商经营分析场景的 Text-to-SQL 智能问数系统：用户以中文口语提问，系统经多轮改写、
> 混合检索、SQL 生成与自省纠错后在数仓执行并返回结果，全链路 SSE 流式可见。

### 核心条目（选 5~6 条，按岗位裁剪）

- **设计并实现 13 节点 LangGraph 问数 Agent**：以查询改写为入口，串联关键词抽取、向量+关键词双路召回、
  RRF 融合、指标口径与 few-shot 注入、SQL 生成与安全校验、自省纠错闭环；
  在 50 条分层评测集（业务 40 + 越界 10）上 **执行准确率 97.5%、SQL 有效率 100%**。
- **构建"数据范围边界 + 拒答"机制**：以 `NO_ANSWER` 协议标记替代模糊 prompt 约束，
  在图中 4 处条件路由实现越界即终止，避免 LLM 编造 SQL；
  实现**拒答准确率 90%、误拒答率 0%**，并输出面向用户的可读引导话术。
- **实现 SQL 自省纠错闭环**：将校验/执行的数据库原始报错回喂模型重写 SQL，最多 3 轮；
  平均尝试 2.0 次即收敛，端到端 SQL 有效率由生成一次的基线提升至 **100%**。
- **建立可复现的评测与消融体系**：自建 50 条 Golden Set（8 类分层）+ 8 条多轮指代集，
  实现 EX / EM / 拒答准确率 / **实体级 Recall@10** / **七子句组件级 F1** 五类指标；
  完成 5 组消融实验，量化各优化项贡献（组件级 F1 86.1 → 92.9），
  多轮改写专项 **87.5% vs 关闭时 37.5%**。
- **工程化收尾**：无状态 JWT 双 Token + RBAC 实现多用户数据隔离；
  滑动窗口限流（业务 `user+path`、认证按 IP 防爆破）；Redis 查询缓存（不可用时降级进程内 TTL，
  **命中 10.4s → 0.1s**）；审计日志与全链路 `request_id`；统一错误码体系（业务码与 HTTP 状态解耦）。
- **全栈容器化交付**：编写后端/前端 Dockerfile 与 9 服务 Compose 编排，
  实现 `docker compose up` 一条命令起全栈；所有连接与 LLM 通道 Env 化，
  切换模型**零代码改动、无需重建镜像**；解决 nginx 缓冲导致 SSE 流式失效等问题。

## 三、每条被追问时的应答定位

### ① 13 节点 Agent

| 追问 | 应答要点 | 代码位置 |
|---|---|---|
| 为什么用 LangGraph 而不是自己写流程？ | 条件边 + 状态机天然表达"自省闭环"和"拒答早退"；`stream_mode=custom` 让每个节点能独立推 SSE 进度 | `app/agent/graph.py` |
| 为什么第一步是改写？ | 用户第二句常是"那华南呢"，不补全的话检索关键词只有"华南"，召回质量崩塌 | `app/agent/nodes/rewrite_query.py` |
| 关键词抽取用不用 LLM？ | 不用。jieba 按词性过滤，零延迟零成本；LLM 只用在真正需要语义判断的地方 | `nodes/extract_keywords.py` |
| 节点失败会不会中断整图？ | 不会。非关键节点（改写、过滤）内部 try/except 回退到"不做处理"的等价态 | 各节点内 |

### ② 拒答机制

| 追问 | 应答要点 |
|---|---|
| 为什么不用 prompt 说"不知道就说不知道"？ | 不可靠。模型倾向给出看似合理的 SQL，**编造的正确数字比报错危险得多**，必须做成协议 |
| 怎么防止误判？ | `is_rejection()` 剥 Markdown 围栏、容忍空白换行，且**要求首行是标记且全文不含 SELECT** 才判拒答 |
| 只在一个节点判吗？ | 四层：`generate_sql` 主判 → 路由函数早退 → `validate_sql` 兜底 → 纠错出口再判 |
| 90% 剩下 10% 是什么？ | "预测下个月销售额"这类预测型问题，模型会尝试用历史均值做外推；可加"预测/建议类意图"规则前置拦截 |

代码：`app/core/rejection.py`、`app/agent/nodes/generate_sql.py`、`app/agent/graph.py` 四个路由函数。

### ③ 自省纠错闭环

| 追问 | 应答要点 |
|---|---|
| 纠错为什么有效？ | MySQL 报错（`Unknown column`、`Unknown table`）本身就是最精确的纠错信号，回喂比盲目重试强 |
| 会不会无限循环？ | `max_retries=3`，`attempt_count` 计数，超限走放弃分支并返回友好错误 |
| 纠错用同一个模型吗？ | 用 `llm_code`（独立配置），代码类任务可单独选型/调参 | `app/agent/llm.py` |
| 代价？ | 每轮一次完整 LLM 调用，平均尝试 2.0 次；因此默认关闭更贵 Self-Consistency |

代码：`app/agent/nodes/correct_sql.py`、`app/agent/nodes/validate_sql.py`。

### ④ 评测与消融（**最加分的一条，务必熟**）

| 追问 | 应答要点 |
|---|---|
| EX 97.5% 但 EM 只有 10%，为什么差这么多？ | **EM 是工程观测指标不是用户指标**：同一查询有无数等价写法（别名、投影列多寡、月份表达式），EM 只衡量"是否与标注一模一样"。用户关心的是结果对不对，所以以 EX 为准 |
| 那怎么区分配置差异？ | 两条路：① 组件级 F1（拆 7 个子句逐项比对，每条样本 7 个判定点）；② 实体级 Recall@10（表/字段/指标是否召回到）。EX 饱和时它们仍能分辨 |
| 消融结论是什么？ | baseline 组件均值 86.1 → full 92.9（+6.8pp），JOIN +18.8pp、WHERE +11.5pp 最大；多轮改写 87.5% vs 37.5% 是最硬的单项证据 |
| RRF 有用吗？ | **诚实答**：当前元数据仅 5 表/2 指标，每路候选 <20 条，RRF 相对并集去重增益有限（EX 持平，字段召回 +2.8pp）。这是规模限制，不是方法无效，结论要限定适用范围 |
| few-shot 会不会泄漏评测集？ | 会，我踩过：原示例库有 5 条与评测集语义邻近，已整体替换为无重合问法，现为纯泛化增益 |

代码：`scripts/run_evaluation.py`、`scripts/run_ablation.py`、`evaluation/*.jsonl`。

### ⑤ 工程化

| 追问 | 应答要点 |
|---|---|
| 多用户数据怎么隔离？ | 无状态 JWT，`user_id` 从 token 解析，会话/消息表按 user 归属；服务不存会话态，可水平扩容 |
| 限流为什么用内存实现？ | 当前单机部署够用且零依赖；接口抽象成 `is_allowed()`，换 Redis 时语义不变可无缝替换 |
| 缓存键为什么带"数据范围"？ | 不同权限用户看到的数据不同，只用问题做键会串数据；且**带历史一律不命中**，防跨会话污染 |
| Redis 挂了怎么办？ | 自动降级进程内 TTL 缓存，问数仍可用（可用性优先） |
| SQL 注入/越权查询怎么防？ | `sql_guard`：关键字/函数/schema 黑名单、强制 LIMIT、行数与字节上限、执行超时；再叠 EXPLAIN 预检。生产还应叠加只读数据库账号 |
| 怎么排查线上问题？ | 全链路 `request_id`（32 位 hex）：响应头 `X-Request-ID` + 日志打点 + `audit_log` 表三处对账 |

代码：`app/core/` 下 `security.py` `rate_limit.py` `query_cache.py` `sql_guard.py` `error_code.py`。

### ⑥ 部署

| 追问 | 应答要点 |
|---|---|
| 一条命令能起来吗？ | 能，`docker compose up -d --build`。`backend-init` 一次性容器保证顺序：TCP 探活 → 建表 → 构建元知识库 → 起后端 → 起前端 |
| 为什么不用 sleep 等依赖？ | `wait_for_deps.py` TCP 探活；qdrant 镜像没 curl/wget 做不了 HTTP healthcheck |
| nginx 有什么坑？ | 默认 `proxy_buffering on` 会把 SSE 攒到最后一次性下发，必须 `off` + `gzip off` + 长 `proxy_read_timeout` |
| uvicorn 为什么单 worker？ | SSE 流式与内存降级缓存依赖单进程状态；扩容靠多容器 + 共享 Redis |
| 模型权重 1.3GB 怎么处理？ | 不进仓库（`.gitignore`），部署文档写明单独下载；CPU 模式 TEI 加载 5~6 分钟已在文档中预警 |

## 四、高频"挑战型"追问

**Q：这个项目不就是调 LLM API 吗，技术含量在哪？**
> 分层答：① 单次调用谁都会，难的是让它在真实库上跑通——自省闭环把有效率从"生成一次"提到 100%；
> ② 难的是让它知道"不该答什么"——拒答机制是产品级要求，不是 prompt 能解决的；
> ③ 难的是证明它有效——自建评测集 + 五类指标 + 消融实验，能量化每个模块贡献；
> ④ 还有一整个工程化体系：多用户、限流、缓存、审计、安全网关、容器化。

**Q：和直接用 ChatGPT 写 SQL 有什么区别？**
> 三点：① 它不知道你的库表结构和指标口径，我们靠双路检索 + 口径注入把企业私有元数据喂进去；
> ② 它写错就错了，我们有自省闭环自动修；③ 它一定会编，我们有边界判定。

**Q：数据这么小（115 笔订单），结论可信吗？**
> 诚实答：这是本项目自建数据集的规模限制（数仓仅 5 表 / 115 笔订单）。因此我把所有结论都限定了适用范围——
> RRF、口径注入这类"依赖元数据规模"的优化，明确写作"小规模下增益有限"而非"有效/无效"。
> 评测方法本身（组件级 F1、实体级召回）才是可迁移的部分。

**Q：EM 这么低，是不是你标注有问题？**
> 标注每条都在 dw 库真实执行通过，且引入了 `gold_sqls` 多参考答案来消除"投影列多寡"造成的伪失败；
> EM 低是因为它衡量的就是"写法一致性"，这恰恰是我不把它当主指标的原因。
