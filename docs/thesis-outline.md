## 二、摘要（中文 300~500 字）要素清单

按顺序交代这 6 点，一段或两段：

1. **背景与问题**：经营分析依赖 BI 看板，临时性追问成本高；通用大模型直接写 SQL 存在
   **领域元数据缺失**、**生成 SQL 不可执行**、**越界问题编造答案**三个问题。
2. **方法**：设计并实现 13 节点 LangGraph 问数 Agent——多轮查询改写、向量+关键词双路召回与 RRF 融合、
   指标口径与 few-shot 上下文增强、SQL 安全网关、自省纠错闭环，以及基于 `NO_ANSWER` 协议的
   数据范围边界拒答机制。
3. **工程实现**：FastAPI 异步服务 + Vue3 前端，JWT/RBAC 多用户隔离、滑动窗口限流、
   Redis 查询缓存与降级、审计日志、统一错误码，Docker Compose 一键部署。
4. **实验**：自建 50 条分层 Golden Set + 8 条多轮指代集，采用 EX/EM/拒答准确率/
   实体级 Recall@10/七子句组件级 F1 五类指标，完成 5 组消融实验。
5. **结果**：EX 97.5%、SQL 有效率 100%、拒答准确率 90%（误拒答 0%）；
   消融显示组件级 F1 由 86.1 提升至 92.9；多轮改写开启 87.5% vs 关闭 37.5%。
6. **结论与局限**：方法有效；元数据规模限制了检索融合类优化的增益空间。

关键词：`Text-to-SQL` `大语言模型` `LangGraph` `混合检索` `RRF` `检索增强生成` `拒答机制`

### 第五章 系统实现与实验（**第二核心章**）

#### 5.1 实现环境

| 项 | 值 |
|---|---|
| 语言 / 框架 | Python 3.12、FastAPI、LangGraph |
| LLM | **必须写明**：如 DeepSeek `deepseek-flash`（官方通道） |
| Embedding | bge-large-zh-v1.5（1024 维，TEI CPU 推理） |
| 存储 | MySQL 8、Elasticsearch 8、Qdrant、Redis |
| 数据规模 | 订单 115 笔、客户 20 人、日期 2025 Q1（90 天），dw 星型模型 5 表 |

#### 5.2 评测集构建

- Golden Set **50 条**：业务类 40 + 越界类 10，按 basic/advanced/challenge 分层，覆盖 8 类
- 多轮指代集 **8 条**（history 内嵌 dw 真实值）
- **标注规范**：gold_sql 必须在 dw 真实执行通过；引入 `gold_sqls` 多参考答案消除"投影列多寡"伪失败
- **防泄漏**：few-shot 示例库与评测集去重（原 5 条重合已替换）

> 表 5-x：类别定义与样本分布表（8 类 × 条数 × 示例）

#### 5.3 评价指标定义（**这节决定答辩上限，务必写清**）

| 指标 | 定义 | 为什么需要它 |
|---|---|---|
| **EX** 执行准确率 | 预测 SQL 与 gold 在 dw 执行结果等价（排序无关逐行比对、浮点相对误差 1e-6、多参考答案任一等价即通过） | **用户价值指标**，主指标 |
| **EM** 精确匹配率 | 归一化（小写/压缩空白/去分号/**剥掉安全网关追加的 LIMIT**）后字符串相等 | 工程观测指标，衡量写法规范性；**不作为结论依据** |
| **拒答准确率 / 误拒答率** | 越界类正确拒答占比 / 业务类被错误拒答占比 | 衡量边界机制 |
| **Recall@10**（表/字段/指标） | gold SQL 所需实体被召回命中的比例，实体级、每条多样本点 | **分辨率高于 EX**，观测检索策略增益 |
| **组件级 F1** | 拆 SELECT/聚合/WHERE/GROUP BY/ORDER BY/JOIN/LIMIT 七子句做集合 F1（两边皆空记满分） | **定位错误环节**，EX 饱和时仍可分辨配置 |

#### 5.4 主实验结果

表 5-x：主评测总表（EX / EM / SQL 有效率 / 拒答 / 召回 / 组件均值 / 平均尝试 / 平均耗时）
表 5-x：组件级 F1 明细（7 列）
表 5-x：分类别指标（8 类）
**bad case 分析**：至少放 1~2 条，说明失败原因（如月度 GMV 的月份表达式写法差异）——有分析才显得真实。

#### 5.5 消融实验

表 5-x：5 组配置对照表（G1→G5，含 EX/EM/有效率/召回/拒答）
表 5-x：组件级 F1 对照表（7 子句 × 5 组）——**最能说明"每个优化项作用于哪个环节"**
表 5-x：成本权衡表（耗时、尝试次数）
表 5-x：多轮专项（87.5% vs 37.5%）+ 逐条对照

**写作要点（直接可用）**：
- "G1→G5 端到端 EX 由 95.0% 提升至 100.0%，但组间差异受样本分辨率（2.5pp/条）与失败样本高度重合影响，
  故引入组件级与实体级指标作为主要观测手段。"
- "组件级均值由 86.1 提升至 92.9（+6.8pp），其中 JOIN +18.8pp、WHERE +11.5pp、SELECT +8.7pp，
  说明优化主要作用于**表关联与过滤条件的生成**，而非聚合函数选择（聚合 F1 各组均在 87.5~95.0）。"
- "多轮专项是查询改写模块的唯一有效观测口径：单轮集无历史可消解，改写增益恒为 0。"

#### 5.6 结果讨论（**必须写局限，这是加分项**）

1. **EX 天花板效应**：业务类仅 40 条，单样本 2.5pp，失败样本高度重合，组间差异被分辨率吞掉。
2. **RRF 在小规模元数据下增益有限**：5 表/2 指标，每路候选 <20 条，截断后两路结果高度重叠；
   k∈[1,100] 实体排名不变。**结论表述为"小规模下增益有限"，而非"RRF 无效"**。
3. **口径注入缺乏区分空间**：仅 2 个指标且定义与自然直觉一致，模型不开注入也能猜中写法。
4. **网关噪声**：若使用免费网关，存在随机 5xx 与模型下架，同配置两次运行可能差 2.5pp；
   正式实验应使用稳定的商业 API 并固定模型版本。
5. **组件级 F1 的局限**：基于字符串/集合比对，无法识别语义等价的不同写法（如 `date_format` vs `substring`），
   因此会低估真实质量，仅作**相对比较**用途。

### 第六章 总结与展望

- 6.1 工作总结（对应三个难点，逐条说解决了没有、解决到什么程度）
- 6.2 创新点（3 条，表述要克制）：
  1. 将"拒答"设计为 Agent 图内的一等分支（协议标记 + 四层拦截），而非 prompt 软约束；
  2. 面向中文口语问数场景构建分层评测集与**多粒度指标体系**（EX / 实体级 Recall / 七子句组件 F1），
     在端到端指标饱和时仍可分辨配置差异；
  3. 完整的工程化闭环：多用户隔离、限流、缓存降级、审计、安全网关与容器化一键部署。
- 6.3 不足与展望：
  - 元数据与数据规模偏小 → 扩充到百表千字段级别，重测检索融合类优化；
  - 限流与缓存为单机实现 → 改为 Redis 分布式；
  - 拒答判定依赖 LLM → 增加意图分类前置规则/小模型判别，降低延迟与成本；
  - 增加查询结果的自动图表选型与自然语言解读；
  - 引入用户反馈闭环（点赞/点踩）持续修正 gold 标注。
